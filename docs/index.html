2. Keputusan desain yang saya ambil

2.1 Mengapa studi kasus CuffnCode?

Roadmap repo menyebut notch 50/60 Hz hum killer — belum ada di firmware STM32. Saya menempatkan algoritma itu di lapisan Host agar tugas paralel punya domain nyata: batch sampel ADC panjang, task filter identik per chunk, dan node terpisah (acquire / process / store).

2.2 Mengapa multiprocessing bukan OpenMP/MPI?

Lingkungan target = laptop Windows mahasiswa + Python scientific stack. Pool.map memetakan langsung ke konsep data parallelism di kuliah; Queue + Process memetakan message passing tanpa cluster. Saya sengaja menambahkan catatan di benchmark ketika speedup < 1 — itu hasil pengukuran jujur di Windows, bukan disembunyikan.

2.3 Notch IIR ditulis manual

Di filters.notch_50hz saya implementasikan koefisien biquad dan state x1,x2,y1,y2 per sampel. Alasan: (1) tugas CPU-bound per chunk untuk paralel; (2) bisa di-port ke CMSIS-DSP/STM32 nanti; (3) menghindari ketergantungan scipy.signal hanya untuk demo.

3. Modul yang saya implementasikan

3.1 signal_generator.py — model fisika + gangguan

Saya menyusun sinyal sebagai superposisi komponen dengan makna oscillometric:

envelope = 80 * exp(-0.35*t) * (1 - exp(-2.5*t))   # kempisan cuff
carrier  = 0.15 * sin(2π * 1.2 * t)                 # osilasi arteri
hum      = 3.0 * sin(2π * 50 * t)                   # PLN 50 Hz (roadmap notch)
noise    = N(0, 0.8)                                # white noise
fs       = 200 Hz, durasi default 24 s (benchmark) / 10 s (GUI)

Parameter seed=42 agar hasil reproduksibel saat dosen menjalankan ulang. Satuan disamakan dengan “mV equivalent” agar konsisten dengan telemetri bridge di GUI.

3.2 cuffncode_specs.py — konstanta dari datasheet/repo

Saya menghitung ulang (bukan mengutip angka bulat saja):

  • Gain AD620: G = 1 + 49400/470 ≈ 106.17 (README menyebut ≈105)
  • Offset TLC2272: divider 47k/56k pada 3.3 V → ~1.79 V di kode, dengan catatan toleransi komponen
  • ADC: 12-bit, 200 Hz — dipakai di hardware_sim._compute_telemetry untuk kode ADC peak

Dictionary PHASE_SPECS berisi teks edukatif per fase (inflate, hold, deflate, AFE, Host) — ditampilkan di panel GUI saat simulasi berjalan.

3.3 hardware_sim.py — state machine

Enum Phase dengan 11 fase: dari PUMP_INFLATE hingga HOST_DISTRIBUTED.

Telemetri yang saya hitung: peak bridge (mV) → dikalikan AD620_GAIN → ditambah TLC_OFFSET_V → dikonversi ke kode ADC 12-bit. Fungsi active_blocks() mengembalikan subset blok diagram yang harus “menyala” per fase — dipakai gui_app._draw_diagram().

3.4 signal_analysis.py — bukti numerik filter

Saya tidak hanya memplot garis hijau/merah — saya menghitung:

  • Daya hum 50 Hz via np.fft.rfft pada band ±3 Hz (fungsi _band_power)
  • Noise residu = std(sinyal − moving average 21 tap)
  • Perubahan peak envelope → mapping demo BP sys = 70 + peak*0.55 (eksplisit: bukan klinis)

Output FilterComparison mengisi panel “PENGARUH pemrosesan” di GUI dengan angka % penurunan hum/noise.

4. Komputasi paralel — detail implementasi

File: Host-Simulation/src/parallel_pipeline.py

4.1 Alur yang saya tulis

  1. generate_cuff_waveform() → vektor N sampel
  2. split_signal(signal, n_chunks=16) → list chunk terindeks
  3. Sequential: for-loop memanggil process_chunk((i, ch, fs, passes))
  4. Parallel: Pool(workers=cpu_count()-1).map(process_chunk, tasks, chunksize=2)
  5. Dynamic: sama dengan chunksize=1 (worker ambil chunk berikutnya saat idle)
  6. merge_chunks — sort by index, np.concatenate (tahap reduce)
  7. Verifikasi: peak_seq ≈ peak_par — jika beda, ada bug race/merge

4.2 Worker process_chunk (filters.py)

def process_chunk(args):
    idx, chunk, fs, passes = args
    filtered = chunk.astype(np.float64)
    for _ in range(passes):          # default 12 pass → beban CPU besar (sengaja)
        filtered = notch_50hz(moving_average(filtered, 11), fs)
    peak = float(np.max(filtered))
    return idx, filtered, peak       # indeks untuk merge yang benar

Saya set filter_passes=12 di benchmark agar perbeda sequential vs parallel terlihat pada CPU; di GUI hanya 4 pass per chunk agar animasi tidak terlalu lama.

4.3 Output terminal yang saya cetak (contoh)

5. Sistem terdistribusi — detail implementasi

File: Host-Simulation/src/distributed_nodes.py

5.1 Tiga proses OS terpisah

FungsiPeranPesan keluar
node_acquisition Memecah waveform 4 batch; sleep(0.05) simulasi streaming ADC {"type":"samples","batch_id", "data"} lalu eof
node_processing Blocking in_q.get(); MA + notch; simpan peak per batch {"type":"features","peaks":[...]}
node_storage max(peaks) → estimasi BP demo Print ke stdout (setara UI/log)

5.2 Mengapa Queue bukan shared memory?

Sesuai materi message passing: tiap node hanya melihat pesan di antrian — mirip pola MPI send/recv pada skala satu mesin. Saya hindari Array shared karena fokus demonstrasi adalah dekompisi subsistem CuffnCode (sensor stream → DSP → tampilan BP).

5.3 Log yang membuktikan eksekusi nyata

[Node A | Acquisition] Streaming selesai.
[Node B | Processing] Batch 0 diproses.
...
[Node C | Storage/UI] Distributed BP estimate: 107/66 mmHg (demo)

6. GUI — apa yang saya bangun

File: gui_app.py — aplikasi tunggal dengan:

  • Diagram Canvas — blok cuff, pump, 2 solenoid, sensor, AD620, TLC2272, STM32, Host, Node A/B/C; warna blok aktif mengikuti active_blocks()

Tema gelap (#1a1d23) dan layout pack dari bawah (log/footer dulu) saya atur supaya tombol “Mulai Simulasi” tidak tertutup grafik pada resolusi 1440×920.
